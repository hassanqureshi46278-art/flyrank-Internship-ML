1

Introduction & Problem Statement

A content or SEO strategist managing a large site cannot review thousands of pages by hand every sprint. Some pages are quietly losing search visibility; others are stale but still pulling in meaningful demand; most are fine as they are. The decision this project supports is narrow and concrete: which pages should a content team review first this sprint, out of a much larger pool of candidates?

The cost of getting this wrong runs in two directions. Flagging a page that's actually fine wastes a writer's scarce hours and delays pages that genuinely needed the work. Missing a page that's quietly decaying means a client keeps losing traffic for another cycle before anyone notices. Because writer time — not model accuracy — is the scarce resource, this project optimizes for the quality of the top of the queue, not for overall accuracy across every page in the portfolio.

This is deliberately framed as a scoring/ranking problem, not a classification problem: the real output a strategist needs is an ordering, not a binary yes/no per page.

Tables and time window

The primary table is fact_content_daily_performance, partitioned by month=YYYY-MM, filtered to one row per page per day. All modeling uses month=2026-03, a mid-panel month — the dataset's final month (June 2026, exposed as the _sample table) is deliberately excluded from training and feature development, since it is the natural outcome window for any past-to-future label and using it early would make any later validation dishonest.

3.3 Leakage audit

Every candidate feature was attacked before being trusted. The clearest case: ctr_28d (clicks ÷ impressions) was initially engineered as a feature, but because it is arithmetically derived from the same clicks signal used in the target, it was leaking the label back in as a feature. It was removed from the final model. A deliberate second leak test — adding a following-month clicks column and watching the quick-fit score jump — confirmed the audit process catches this class of error before it reaches a shipped model.

3.4 Baseline (Week 4)

The baseline is a single hand-written rule: a weighted combination of normalized staleness and normalized search volume, producing one action score, one reason code (STALE_HIGH_DEMAND), and a binary action label. Two signals behind the rule were checked against real bucket tables before encoding it — see §4 for the verdicts.

3.5 Model and validation design

A Random Forest Regressor was chosen over a linear baseline because the underlying signals (staleness, demand, position) plausibly interact rather than contribute independently, and because it provides permutation importance for interpretation. Validation uses a client-grouped split (not a naive random split): pages belonging to the same client are kept entirely in either train or test, since a random split would let correlated pages from one client leak signal across the boundary and overstate performance.

Limitations & Honest Framing

Correlational, not causal. Every relationship reported here — staleness, demand, position — is observed in one anonymized month. None of it proves that changing a feature (e.g., refreshing a page) causes a specific outcome, the same caveat FlyRank's own March 2026 research paper applies to its refresh-multiplier finding.

Unbalanced panel. Per-client history depth differs (dim_clients.gsc_data_start / ga4_data_start), so early rows for newer clients may be GSC-only, which could quietly bias any feature that assumes both sources exist.

Single-month training window. The model has not been validated across multiple months or a true time-based split; a client-grouped split protects against client leakage but not against seasonal drift.

Proxy label, not ground truth. The target used here is a defined stand-in, not an observed "refresh worked" outcome — see §3.1.

6

Ranked Recommendations

  1. Refresh stale, high-demand pages first
    Highest action-score archetype in this ranking; matches the clearest measured lever in FlyRank's own portfolio research.
  2. Improve snippets on already-page-one pages
    Click-capture gains compound faster here than building new pages from scratch.
  3. Monitor, don't touch, young/fresh pages
    Still in the natural growth window; premature action here wastes review time.
  4. Re-audit signals before applying this queue to a new client vertical or month
    Signal verdicts in §4.1 were confirmed on one slice; they are not guaranteed to generalize.

Intended use, human review, and the no-go list

This ranking is decision-support for a content strategist with editorial judgment — not an automated publishing or deletion pipeline. Before acting on any recommendation, a human should confirm the page isn't intentionally seasonal or quiet, isn't under legal/compliance hold, and that the assigned reason code actually matches the page's real situation.

Never automate: publishing content changes directly from this queue; removing a page because it scored low; treating an archetype label as a public claim about content quality.

Monitoring / retrain triggers

  • Precision on a fresh month drops below the Week-4 baseline's rate → retrain.
  • Feature distributions shift materially from the training month → re-run the signal audit before trusting the queue.
  • A new client vertical is added → re-verify signals for that vertical specifically.
  • Reviewers reject the majority of top recommendations across several sprints in a row → pause and investigate.
